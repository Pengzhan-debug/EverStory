# 测试技术栈与系统测试实验

日期：2026-10-21。目标：为软件测试 / AI 测试求职补充可复现的接口、页面和性能测试实践。

## 1. Requests 是否需要

需要掌握，Python 库名是 **requests**。本项目已经在模型 HTTP 传输层使用它，本次还增加了
`qa/http/test_requests.py`，通过真实 TCP/HTTP 服务执行测试。

| 工具 | 本项目的用途 | 关键能力 |
| --- | --- | --- |
| pytest | 测试组织和执行 | fixture、参数化、断言、Mock、JUnit、覆盖率 |
| Requests | 真实 HTTP 冒烟测试 | Session/Cookie、CSRF、JSON、连接/读取超时、SSE 逐行解析 |
| HTTPX / FastAPI TestClient | 进程内接口回归 | 隔离数据库、替换模型、注入超时和写入冲突 |
| Playwright | 真实浏览器页面流程 | Page Object、自动等待、响应监听、多上下文、路由故障、截图/trace |
| Allure | 结果展示和证据 | 用例状态、参数、页面截图、SSE JSON 附件 |
| Locust | 并发 HTTP 负载 | HttpUser、权重、思考时间、Session 隔离、业务断言、CSV/HTML 指标 |
| GitHub Actions | 自动执行 | 原有单元/API/基础设施测试；新增系统测试和 Allure artifact |

Requests 不需要替换现有 HTTPX。两套接口测试分别覆盖真实网络传输和进程内故障注入。
Locust 的 HttpUser 客户端也基于 Requests，但不会执行页面 JavaScript；页面流程由 Playwright 检查。

## 2. 新增用例和验收方式

**6 项真实 HTTP 用例，全部通过：**

1. Session 获取并复用三个 Cookie；合法 JSON 行动返回值与再次 GET 的持久化状态一致。
2. 缺少 CSRF Token：403，状态哈希不变。
3. 错误 CSRF Token：403，状态哈希不变。
4. 截断 JSON：400 且包含错误信息，状态哈希不变。
5. SSE 使用 `stream=True`、17 字节读取块及 `iter_lines()` 解析；最后一个事件为 `done`，
   `done` 恰好一次、无 `error`，完成事件的世界哈希与 GET `/api/world` 一致。
6. 存档、执行新回合、读档恢复；另一个 Session 不能读取该存档且自己的回合保持 0。

**10 项页面流程，全部通过：**

- 提交行动后 SSE 叙述、位置 HUD 和服务端状态一致。
- 无效地点不修改世界事实；输入框恢复可用，下一次合法行动能成功。
- 调查组产生提案后世界不变；用户点击批准后世界推进。
- 工具栏保存、继续行动、读取后恢复原状态。
- 刷新后世界状态及原始指令保留，界面展示对应的本地化文案。
- 切换中文、刷新后保留语言选择且世界事实不变。
- 两个 BrowserContext 使用独立 Cookie，世界状态互不污染。
- 中止一次行动网络请求，错误提示出现、输入恢复，重试可以成功。
- 打开设置弹窗再关闭，原游戏状态保留。
- 390×844 窄视口能够提交行动。

页面通过 DOM、网络响应和服务端状态交叉断言，Allure 保存最终页面截图。失败时 pytest-playwright
配置保留截图和 trace；首轮测试预期修正过程也留有本地失败证据。此次正式结果无失败重试。
本地执行浏览器是 **Google Chrome 154.0.8037.98，Windows 10，headless**；没有据此声称完成
Firefox、WebKit 或真实手机兼容性测试。窄视口只验证交互可用性，不等于完整视觉验收。

**原有回归：222 通过、3 跳过，另有 17 个 unittest subtest 通过。** 跳过的 3 项需要独立
PostgreSQL/Redis 服务；上一轮 CI 已在真实 PostgreSQL 16 / Redis 7 上通过这些用例。

注意：引擎的 `turn` 统计行动尝试，失败行动也可能增加回合数；`state_hash` 只比较世界事实，
不能单独证明回合没有变化。新增压测同时检查回合数、位置和哈希。

## 3. Locust 实验设计

- 目标仅接受 `127.0.0.1` / `localhost`，并校验 QA 服务专用响应头。
- 使用真实 Uvicorn HTTP 服务、临时 SQLite 数据库和内存会话协调；模型客户端强制 Stub。
- 每个用户通过 `/api/auth/session` 获取独立 Cookie 和 CSRF Token。
- 请求权重 `GET /api/world : POST /api/turn(wait) = 3:1`，不是固定请求数量比例。
- 每次任务后等待 100–300ms；用户数和每秒请求数是不同的指标。
- 5、15、30 用户各重复两轮，每轮时限 30 秒；另运行 15 用户、时限 120 秒的短时持续测试。
- 目标用户约 1 秒内启动，统计包含初始化和爬升；没有独立预热窗口。实际请求统计窗口以
  Locust CSV 的请求数 / Requests/s 为准，可能短于 CLI 时限。
- 每个用户维护期望回合：写请求必须递增 1；读请求必须看到本用户的回合、位置及最近哈希。
  语义不一致也记为失败；不只检查 HTTP 200。
- 导出请求数、失败数、RPS、平均值、P50/P95/P99，保留各接口分项。Locust 分位数使用分桶近似。


| 运行 | 请求数 | 失败数 | RPS | P50(ms) | P95(ms) | P99(ms) |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| step-5u-r1 | 503 | 0 | 18.56 | 47 | 150 | 300 |
| step-5u-r2 | 537 | 0 | 19.13 | 44 | 120 | 170 |
| step-15u-r1 | 709 | 0 | 26.01 | 260 | 1100 | 1700 |
| step-15u-r2 | 746 | 0 | 29.35 | 280 | 660 | 960 |
| step-30u-r1 | 1009 | 0 | 34.37 | 610 | 1200 | 1400 |
| step-30u-r2 | 1109 | 0 | 38.64 | 540 | 1000 | 1300 |
| soak-15u-r1 | 3924 | 0 | 32.97 | 240 | 460 | 600 |

正式 7 轮的 CSV 共记录 8537 次请求、0 次失败（包含初始化请求及业务语义校验）。CSV 为停止时的统计快照，退出时在途请求完成后，终端最终计数可能略多。30 用户两轮 P95 为 1200 / 1000ms，吞吐为 34.37 / 38.64 RPS。并发升高后延迟明显上升；尚未做 CPU、SQL 锁等待剖析，因此不归因于单一组件。

实测汇总见 [results.json](results.json)。本机 CPU 同时承载服务端和负载生成器，结果用于建立
项目基线；不能作为线上 PostgreSQL/Redis、多进程部署、真实模型吞吐或模型生成延迟的结论。
120 秒仅为短时稳定性检查，尚未进行小时级稳定性、内存泄漏和容量上限定位。

## 4. 复现

在仓库根目录执行；建议新建虚拟环境。`qa/` 不在默认 `testpaths` 中，普通测试不要求安装这些可选依赖。

```powershell
python -m pip install -e ".[web,test,qa]"
python -m playwright install chromium
python -m pytest tests -q
# 自动启动临时真实 HTTP 服务；输出目录必须是新的，防止混合多次 Allure 结果。
python scripts/run_system_qa.py --out reports/system-qa/artifacts/run-01
# 已安装 Chrome 时可使用 --channel chrome；其他浏览器需先安装对应的 Playwright 浏览器。
# 分别运行接口和页面测试：
python -m pytest qa/http -q
python -m pytest qa/browser --browser chromium --tracing retain-on-failure
```

只运行其中一部分可加 `--skip-load` 或 `--skip-functional`。完整压测约 5–7 分钟。
脚本失败时保留对应日志、CSV 和 HTML；不要把未完成的运行计为通过。API/浏览器测试通过后，
可在同一输出目录以 `--skip-functional` 补跑负载测试。

```powershell
npm ci --prefix qa
node qa/node_modules/allure/cli.js awesome reports/system-qa/artifacts/run-01/allure-results --single-file --output reports/system-qa/artifacts/run-01/allure-report
node qa/node_modules/allure/cli.js open reports/system-qa/artifacts/run-01/allure-report
```

默认 CI 运行接口/浏览器验收并上传 Allure/JUnit/失败截图/trace。性能基线在本机按需运行，
避免共享 CI 主机的噪声造成不可靠的耗时门禁。目前没有设定未经业务确认的延迟 SLA。

## 5. 面试时如何解释

- **为何还用 Requests？** 增加真实网络服务验证，学习 Session、Cookie、CSRF、显式超时、流式响应；
  HTTPX/TestClient 保留用于更方便地注入服务端故障。
- **pytest 和 Requests 的区别？** pytest 管理用例和断言；Requests 发送 HTTP 请求，可以组合使用。
- **为何 HTTP 200 不够？** 有可能回合串会话、重复执行或返回未提交状态，所以继续检查世界事实和持久化结果。
- **P95 是什么？** 按响应耗时排列，约 95% 的请求耗时不超过该值；同时看分接口数据和失败率。
- **为何不写真实模型高并发？** 本次测试对象是 Web/状态链路。真实模型需另外控制配额、预算和供应商延迟，
  与 Stub 性能数据分别报告。
- **AI 评测还缺什么？** 当前固定案例及历史输出复算不能替代独立测试集；后续需要新样本、恶意提示、
  多轮偏离、证据污染和人工复核，并按准确率/来源正确性/拒绝率/成本分别报告。
